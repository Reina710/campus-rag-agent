# 校园知识库问答 Agent —— 从零手写 RAG，用 29 题量化检索的每一层

> 不依赖任何 Agent 框架，从零手写一个"检索即工具"的问答 Agent。它最有价值的地方不是"能做问答"，而是**每一层都有一个能复现、能对比的数字**——包括诚实承认自己的短板。

---

## 它在解决什么问题

大部分 RAG 项目止步于"我接了 LangChain / Chroma，效果不错"。这个项目做的事更进一步：**把"效果不错"这句话拆开，逐层量化。**

- 检索强不强？—— 四种检索器在同一套题库上对比，量出命中率、recall@K、MRR
- 哪里强、哪里漏？—— 用 recall@K 把"跨块信息捞不全"这个隐性短板钉死成 `0/2 → 1/2 → 2/2`
- 检索对了就够了吗？—— 端到端发现"检索命中 96.6%，回答通过率却停在 93.1%"的断层

**核心结论：检索只是 RAG 的第一层，真正难的在后面。**

---

## 架构

```
用户提问
   ↓
Agent 主循环（ReAct，模型自主决定查不查、查几次、要不要换词重查）
   ↓
检索（包成工具 search_knowledge，而非写死的 pipeline）
   ├─ freq   字频（免费，基线）
   ├─ bm25   分词 + IDF（免费）
   ├─ embed  向量（阿里云 text-embedding-v3，含索引落盘）
   └─ rrf    bm25 + embed 融合
   ↓
上下文拼装（Top-K 块 + 防注入信封 <untrusted_data>）
   ↓
生成（DeepSeek，资料里没写的就说"没写"，不编）
```

关键设计：检索不是写死的一步，是**工具**。模型自己决定要不要查、查完不满意要不要换词再查——这是它和"检索→拼 prompt→生成"流水线的本质区别。

## 评测数据（核心，全部可复现）

### 检索层：四种检索器，同一套题库（27 道非陷阱题，知识库 38 块，Top-K=3）

| 检索器 | Top-1 命中 | Top-K 命中 | recall@3 | MRR |
|---|---|---|---|---|
| freq 字频 | 81.5% | 92.6% | 0.926 | 0.864 |
| bm25 分词+IDF | 88.9% | 100% | 0.982 | 0.944 |
| **embed 向量** | **96.3%** | **100%** | **1.000** | **0.982** |
| rrf 融合 | 92.6% | 100% | 1.000 | 0.963 |

三个指标各管一维：Top-1 看"准不准"、recall@K 看"漏没漏"、MRR 看"排得早不早"。光看命中率会漏掉一半真相。

### 三个能经得起追问的结论

**1. recall@K 把"跨块短板"量化了。** 某题答案散在"实习黄金时间"+"秋招时间"两块：freq `0/2`（一块没捞到）、bm25 `1/2`（漏一半）、embed `2/2`（全中）。命中率只会说"中没中"，recall@K 才能说"漏了几个"。这是字面检索的天然短板——按字匹配，捞不到"意思相关但字面不重复"的另一块。

**2. MRR 暴露排名精度。** embed 的 MRR 0.982 = 正确块几乎次次第一；freq 只有 0.864 = 命中了也常排在二三。向量检索不只"捞得回"，还"排得准"。

**3. 反直觉：RRF 没打赢 embed。** 很多人默认"融合一定更强"，但实测 embed 已经 100% 命中、recall 1.0，rrf 没有发挥空间，反而 Top-1 略降（92.6% < 96.3%）——引入了 bm25 的字面噪声。**单路已经够强时，融合反而被弱路拉低。**

### 端到端：检索对了，答案就对了吗？

| 检索器 | 检索命中率 | 回答通过率 |
|---|---|---|
| freq | 93.1% | 93.1% |
| embed | 96.6% | 93.1% |

embed 检索命中率更高（多捞回一道跨块题），但**回答通过率两边一样**。因为跨块题的答案分散在多块，Top-K=3 只装得下一块，模型拿到的上下文还是不完整。

> **换检索器能把"该捞的块"捞出来，但把分散的信息拼成完整答案，是 RAG 更深一层的问题**——要靠更大的 Top-K、多路融合或重排（rerank）解决。

### 切块参数对照（freq，同一套题只变切法）

| 切块方式 | 块数 | 命中率 | 标志词召回率 |
|---|---|---|---|
| heading 按标题 | 38 | 100% | 79.1% |
| fixed 300 字 | 19 | 100% | 81.7% |
| fixed 500 字 | 11 | 100% | 81.7% |
| fixed 800 字 | 7 | 100% | 81.7% |

结论：300/500/800 召回率完全一样——知识库只有七千多字，切块字数在这个量级**不敏感**。选 heading 不是因为数字高，是因为校园知识天然"一个标题一个知识点"，语义更干净。

## 踩过的坑（每个都是亲手撞出来、再亲手量出的）

1. **字频把"看起来像"的捞上来** —— 问"什么是 RAG"，Top-1 居然是"ReAct 循环"（因为 RAG 三个字母 ReAct 里全有）。Top-K=3 兜住了。→ Top-K 是在给检索的失误留余量，代价是上下文多塞无关资料。
2. **真正的注入不是"喊口号"，是"篡改事实"** —— 转账/忽略规则类注入 DeepSeek 天生免疫；换成"伪装教务处改选课时间"才测出干净差异：裸版被骗，加固版守住。对策 = `<untrusted_data>` 信封隔离。
3. **删了关键信息，模型不说不，会编一个更自信的错答案** —— 硬砍"研二专硕找算法实习"后，模型编出"你是大三本科生想找 Java"。→ 上下文压缩不是省空间，是保住关键事实不被幻觉顶掉。
4. **tool_call_id 活不过一次重启** —— 把 tool 中间产物存进文件，重启成死链。→ 持久化只存干净问答，滤掉 tool 产物。
5. **向量检索 37 次请求 → 冷启动 2 次** —— 缓存（治重复算）+ 批量（治来回打车）+ 落盘（治重启重算）三层优化。

## 快速开始

```bash
pip install -r requirements.txt   # 只依赖 openai + jieba，其余全是标准库
cp .env.example .env              # 填 DEEPSEEK_KEY 和 DASHSCOPE_KEY
```

然后：

```bash
双击 run.bat        # 对话（/hits 看检索命中了哪几块，/history /clear）
双击 run_eval.bat   # 跑评测，结果落盘 reports/
```

## 技术栈

Python 3.11+ · DeepSeek（对话）· 阿里云 text-embedding-v3（向量）· jieba（分词）

不依赖任何 Agent 框架 —— 循环、检索、上下文拼装、评测全部手写。

## 目录结构

```
src/        核心代码（config / knowledge 切块 / retriever 四检索器 / agent 主循环 / evaluate 评测）
demos/      演示脚本（防注入 / 按 token 裁剪 / 压缩对照 / 工具安全层 / 向量优化）
data/       知识库 + 注入攻击样本
reports/    评测报告（自动生成，不入库）
```
