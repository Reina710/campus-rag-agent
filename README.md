# 校园知识库问答 Agent

> 面向校园知识库的 RAG Agent：ReAct 循环 + 5 种可插拔检索器 + 214 题系统化评测 + 可上线的 Web 服务。
> 不依赖任何 Agent 框架，每一层都有可复现的量化结果。

**一句话**：把"接了 RAG，效果不错"这句话拆开，逐层量化；再把它做成一个能上线、能引用出处、能管理知识库的产品。

---

## 30 秒速览

| 维度 | 数据 |
|---|---|
| 知识库 | **54 块** / 10 大类（培养、选课、实习、校招、论文、日常、奖助、竞赛、国际交流、导师） |
| 题库 | **214 题**：常规 158 / 跨块 23 / 易混淆 6 / 陷阱 15 / 注入 12 |
| 检索 | **5 种方案**同台对比，Top-1 从 76.4%（字频）到 **96.0%**（宽召回 + RRF + rerank） |
| 独立评测集 | **65 题 holdout**（62 道参与检索指标），不参与调参 |
| 端到端 | SSE 流式、引用溯源（`[n]` + 来源卡片）、多会话、文档上传、点赞点踩 |
| 部署 | Docker 多阶段构建 + gunicorn + 健康检查（`/livez` `/readyz`）+ Prometheus |

## 这个项目值得看的 4 点

1. **逐层量化，不靠"感觉不错"。** 字频 / BM25 / 向量 / RRF / 宽召回+rerank 五种检索器在同一套 214 题上对比，量 Top-1、Top-3、recall@K、MRR，并按难度层（L1 直问 / L2 改写 / L3 细节 / L4 口语）拆开看。
2. **一个 bug 让结论反转。** BM25 原实现写成 `TF × IDF ÷ 块长度`（缺 TF 饱和、长度惩罚过猛），修好后 BM25 Top-1 从 71.4% 涨到 83.9%，"融合不占优"的结论直接反转成"融合占优"。这件事本身比任何指标都值得讲。
3. **评测集和调参集分开。** 214 题里按知识块分层抽出 65 题做独立评测集，调参只用另外那部分，最终指标只在 holdout 上报，避免"在评测集上调参"。
4. **从 demo 到可上线。** 会话隔离、限流、并发闸门、流式 SSE、降级（rerank→RRF、向量→BM25）、启动自检、预热、健康检查、JSON 日志、`/metrics`，都是按"真上线"做的。

## 架构

```
用户提问
   ↓
查询改写（可选）：把问题改写成 2-3 个检索版本，含指代消解
   ↓
Agent 主循环（ReAct，模型自主决定是否检索、是否换词重查）
   ↓
检索（封装为工具 search_knowledge，可插拔）
   ├─ freq   字频（基线）
   ├─ bm25   分词 + IDF（标准 BM25：TF 饱和 + 长度惩罚）
   ├─ embed  向量（阿里云 text-embedding-v3，索引落盘）
   ├─ rrf    bm25 + embed 融合（k=60）
   └─ hybrid 宽召回（每路 20）→ RRF 合并（10）→ rerank 精排（3）
   ↓
上下文拼装（Top-K 块 + 防注入隔离 <untrusted_data>）
   ↓
生成（DeepSeek，仅依据资料回答，缺失则明确说"资料里没写"）
   ↓
引用溯源：答案标 [n] + 命中块推给前端渲染成来源卡片
```

**关键设计**：检索以工具形式接入，由模型自主决定调用时机与次数，区别于固定的"检索 → 拼 prompt → 生成"流水线。不依赖 LangChain / LlamaIndex，是为了能单独量出每一层的贡献。

## 评测（重点）

### 检索层：五种方案对比

| 检索器 | Top-1 命中 | Top-3 命中 | recall@3 | MRR |
|---|---|---|---|---|
| freq | 76.4% | 94.0% | 0.915 | 0.844 |
| bm25 | 83.9% | 95.0% | 0.925 | 0.890 |
| embed | 88.9% | 99.0% | 0.980 | 0.936 |
| rrf | 89.9% | 97.0% | 0.957 | 0.931 |
| **hybrid（宽召回 + RRF + rerank）** | **96.0%** | **100%** | 0.985 | **0.980** |

**holdout 独立集（62 题，未参与调参）**：freq 80.6% / bm25 87.1% / embed 90.3% / rrf 93.5% / **hybrid 96.8%**——与全量基本一致，无过拟合迹象。

### 三个能讲出来的结论

1. **数字涨跌要先看分母。** 向量单路在 29 题 96.3%、150 题 86.2%、190 题 83.4%、214 题 88.9%——四个数字对应四种题库和知识库结构，不能直接比。83.4 → 88.9 的主因是知识库从 39 块重构成 54 块（块粒度变了），不是补了内容。
2. **融合是否占优，取决于被融合那一路的质量。** BM25 有 bug 时 RRF 输给纯向量；修好后 RRF 反超。**同一句"融合不占优"，换一个 bug 就反转**——所以看到融合没涨，先怀疑单路实现，再怀疑融合策略。
3. **排序该交给能读内容的模型。** 宽召回（每路 20）→ RRF 合并（10）→ rerank 精排（3）把 Top-1 从 89.9%（全量 RRF）提到 96.0%，是收益最大的一步：相对全量 RRF +6.1 个点，相对最强单路（向量 88.9%）+7.1 个点。

### 切块对照

| 切块方式 | 块数 | Top-3 命中 | 标志词召回 |
|---|---|---|---|
| **heading 按标题（采用）** | 54 | 94.5% | 80.1% |
| fixed 300 字 | 26 | 94.0% | 80.6% |
| fixed 500 字 | 15 | 91.0% | 80.6% |
| fixed 800 字 | 9 | 95.5% | 83.0% |

四种切法命中率差异不大（91%～95.5%）。仍选 heading：校园知识天然"一个标题一个知识点"，按标题切语义边界清晰、引用能直接定位；fixed 会在标题中间断开，跨块题反而更难拼。

### 回答质量：LLM-as-judge

关键词匹配只能测"关键数字有没有出现"，测不出答非所问和编造。所以加了一层 LLM-as-judge，按 **faithfulness**（是否只依据资料）和 **relevance**（是否回答了问题）各打 1-5 分：

```bash
python src/eval_judge.py --limit 5 --split holdout
```

### 调参 / 考试分开跑

```bash
python src/eval_retrieval.py --split dev      # 调参集
python src/eval_retrieval.py --split holdout  # 独立评测集（报成绩用）
python src/eval_pipeline.py --split holdout   # 五方案对照
```

CI 每次 push 跑离线门禁（不联网、不需要密钥）：`python experiments/ci_gate.py`，freq / BM25 的 Top-1 低于 74% / 81% 判定退化。

## 工程能力

| 能力 | 实现 |
|---|---|
| 会话隔离 | 按 cookie 分配会话，历史按会话落盘，访客之间不共享上下文 |
| 多会话 | 同一浏览器多段对话，记忆按 `<sid>__<conv>.json` 隔离，可切换/新建/删除 |
| 并发 | 每会话一把锁，同一用户请求串行；全局并发闸门（默认 8）满了直接 503 不排队 |
| 流式 | `POST /ask_stream` 返回 SSE，先给 `status`/`hits` 再逐段吐 `delta`，支持 `reset` 撤回思考内容 |
| 引用溯源 | 答案结论后标 `[n]`（对应资料编号，只标真正用到的）；命中块先于答案推送，前端渲染为可展开的来源卡片 |
| 文档管理 | 上传 `.md/.txt` 自动切块入库，增量补向量；支持删除、重建索引 |
| 查询改写 | 检索前把问题改写成 2-3 个版本（含指代消解），多路召回后合并；失败退回原问题 |
| 反馈 | 回答下方 👍/👎，落 `data/feedback.jsonl`，点踩的题就是 bad case 池 |
| 降级 | rerank 失败回退 RRF 顺序；向量服务失败回退 BM25；模型超时返回可读提示而非 500 |
| 限流 | 同一 IP 每分钟 12 次，超限返回 429 |
| 启动自检 | 知识库为 0 块、检索器名字写错、目录不可写 → 拒绝启动；缺 key 只告警 |
| 预热 | 启动时初始化 jieba 词典、算好块向量，避免第一个访客等冷启动 |
| 健康检查 | `/livez` 看进程、`/readyz` 看能否服务、`/health` 给监控看依赖状态 |
| 可观测 | 一行一个 JSON 的日志（带 `rid` 可串一次请求）+ `/metrics`（Prometheus 文本） |

**为什么是单进程**：会话状态在进程内存中，多 worker 时同一用户的两次请求可能落到不同进程，表现为刷新后历史丢失。要横向扩容需把会话移到 Redis，路线写在 `DEPLOY.md` 第 8 节。

## 工程记录（踩过的坑）

1. **BM25 的长度惩罚写反了。** 原实现 `TF × IDF ÷ 块长度`，缺 TF 饱和项，40 字的块无条件压过 200 字的块。修成标准 BM25（k1=1.5, b=0.75）后 Top-1 71.4% → 83.9%；同一天在 L3 细节题上，hybrid 从 75.0% 提到 98.4%。
2. **融合的结论被一个 bug 反转。** 见上。教训：看到融合没涨，先怀疑单路实现。
3. **注入攻击要构造有效样本。** 转账/忽略规则类指令对 DeepSeek 无效；用"伪装教务处修改选课时间"这类事实篡改样本，才测出加固版（`<untrusted_data>` 信封）和未加固版的差异。
4. **上下文压缩会丢关键事实并引发幻觉。** 删掉"研二专硕找算法实习"这句后，模型生成了错误推断。压缩的目标是保证关键事实不被覆盖，不只是省空间。
5. **流式只解决一半问题，另一半是冷启动。** 接入 SSE 后首字节仍要 11.3 秒；把 jieba 词典、块向量预热挪到启动阶段后，首字降到约 2 秒、命中块 1.4 秒就显示。**用户感知的等待不是总耗时，是"第一屏有东西"的那一刻。**
6. **探针不能拿依赖状态做判断。** `/health` 缺 key 时返回 `degraded`，直接当容器探针会让平台把"欠费"当成"进程挂了"反复重启。所以拆成 `/livez` 和 `/readyz`。
7. **流式下"已显示的内容"可能是错的。** Agent 会先说一句"我查一下资料"再去调工具，这句会作为正文推给前端。协议里加 `reset` 事件撤回——验收测试真的抓到了这条路径，不是纸上设计。

## 快速开始

```bash
pip install -r requirements.txt
cd frontend && npm ci && npm run build && cd ..   # 首次构建前端，产物落到 static/
cp .env.example .env                              # 填 DEEPSEEK_KEY / DASHSCOPE_KEY
python web_demo.py                                # 打开 http://127.0.0.1:8000
```

没构建前端也能启动，会回退到 `templates/index.html` 的旧版页面。

命令行模式：

```bash
python src/app.py          # 对话（/hits 看检索命中，/history /clear）
python src/evaluate.py     # 端到端评测
```

## 部署

```bash
cp .env.example .env          # 填 DEEPSEEK_KEY / DASHSCOPE_KEY / APP_SECRET
docker compose up -d --build
curl -s localhost:8000/readyz
```

- 多阶段构建：`node:20-alpine` 里跑 `npm ci && vite build`，产物拷进 python 镜像，node 不进最终镜像。
- 生产启动：`gunicorn -w 1 --threads 16`（单进程多线程，原因见上），容器非 root。
- 完整步骤、反向代理、排障表见 [DEPLOY.md](DEPLOY.md)。

python tests/test_online.py http://127.0.0.1:8000

## 技术栈

**后端**：Python 3.11+ · DeepSeek · 阿里云 text-embedding-v3 · gte-rerank-v2 · jieba · Flask · gunicorn

**前端**：React 18 · Vite 5 · Tailwind CSS（产物为静态文件，无独立前端服务）

**不依赖 Agent 框架**：ReAct 循环、检索器、rerank、上下文拼装、评测均为自行实现。

## 已知边界

- 知识库里的"图书馆/食堂/宿舍"等 8 类是**示例内容**，按通用校园信息撰写，上线前需替换为本校真实信息；培养方案大类为真实培养方案。
- 会话状态在进程内存，**只支持单进程**；横向扩容要先迁移到 Redis。
- 单文件上传上限 512KB，只支持 `.md` / `.txt`（PDF/Word 解析未做）。
