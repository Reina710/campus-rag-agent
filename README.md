# Campus Knowledge-base QA Agent

> 一个面向校园知识库的问答 Agent：ReAct 循环 + 可插拔检索器 + 系统化评测。
> 不依赖任何 Agent 框架，各层均有可复现的量化评测结果。

## 项目定位

多数 RAG 项目的结论停留在"接了框架，效果不错"。本项目的重点是把这句话拆开，逐层量化：

- 检索质量：五种方案（字频 / BM25 / 向量 / RRF / 宽召回+rerank）在 214 题上对比，评测 Top-1、recall@K、MRR
- 检索短板：用 recall@K 量化答案跨块时的召回缺失，`0/2 → 1/2 → 2/2`
- 端到端断层：29 题早期版本上检索命中率 96.6%、回答通过率 93.1%——定位到 Top-K 上下文容量问题

## 架构

```
用户提问
   ↓
Agent 主循环（ReAct，模型自主决定是否检索、是否换词重查）
   ↓
检索（封装为工具 search_knowledge，可插拔）
   ├─ freq   字频（基线）
   ├─ bm25   分词 + IDF
   ├─ embed  向量（阿里云 text-embedding-v3，索引落盘）
   ├─ rrf    bm25 + embed 融合
   └─ hybrid 宽召回（每路 20）→ RRF 合并（10）→ rerank 精排（3）
   ↓
上下文拼装（Top-K 块 + 防注入隔离 <untrusted_data>）
   ↓
生成（DeepSeek，仅依据检索到的资料回答，缺失则明确说明）```

关键设计：检索以工具形式接入，由模型自主决定调用时机与次数，区别于固定的"检索 → 拼 prompt → 生成"流水线。

## 评测数据

### 检索层：五种方案对比

知识库 54 块（10 大类 + 新增的图书馆/食堂/宿舍/体育/交通/党团/学籍/就业 8 类），题库 214 题（常规 158 / 跨块 23 / 易混淆 6 / 陷阱 15 / 注入 12），其中 199 道有标准答案的题参与检索指标。
另设 65 题独立评测集（holdout，按知识块分层抽样、每块至少 1 题）：调参只用其余 149 题，最终指标在 holdout 上报告，避免"在评测集上调参"。

| 检索器 | Top-1 命中 | Top-3 命中 | recall@3 | MRR |
|---|---|---|---|---|
| freq | 76.4% | 94.0% | 0.915 | 0.844 |
| bm25 | 83.9% | 95.0% | 0.925 | 0.890 |
| embed | 88.9% | 99.0% | 0.980 | 0.936 |
| rrf | 89.9% | 97.0% | 0.957 | 0.931 |
| **hybrid（宽召回 + RRF + rerank）** | **96.0%** | **100%** | 0.985 | **0.980** |

holdout 独立集（62 题，未参与调参）：freq 80.6% / bm25 87.1% / embed 90.3% / rrf 93.5% / **hybrid 96.8%**，与全量基本一致，无过拟合迹象。

> bm25 一行的打分公式在 2026-10-23 修正：原实现是 `TF × IDF ÷ 块长度`，缺 TF 饱和项、长度惩罚也不对，导致 40 字的块无条件压过 200 字的块。修正后 bm25 全量 Top-1 71.4% → 83.9%，细节题（L3）75.0% → 98.4%（hybrid）。
> 同日补全了竞赛、国际交流、导师与实验室三节共 6 个内容过短的块（原 36~50 字，答不出任何细节）。这几块按研究生培养的通用流程撰写，具体细则以学校当年通知为准，属于示例内容。

### 结论

1. **跨口径的数字不能比。** 向量单路在 29 题 96.3%、150 题 86.2%、190 题 83.4%、214 题（54 块）88.9%——四个数字对应四种题库和知识库结构，涨跌都不能直接归因到某一个改动。83.4 → 88.9 的主因是知识库从 39 块重构成 54 块（块粒度变了），不是补了 6 个短块。
2. **补内容不改变检索指标，改变的是回答的细节量。** 受控实验（只把 6 个块换回原版，其余不动）在 17 道相关题上：bm25 94.1% → 100%，其余三路 Top-1 完全不变。差别落在回答里——问「出国交换之前要做什么准备」：

   > 旧版：资料里只提到有交换生项目、学分可认定但需提前规划，**具体申请材料和流程资料里没写**。
   >
   > 新版：关注通知 → 提交申请（成绩单、语言成绩、研修计划、院系推荐意见）→ 学院推荐与学校评审 → 对方录取 → 签证派出；语言通常要求雅思 6.0 或托福 80 以上。最关键的是出发前做课程对接……

   **指标测不出这种改善，是因为检索名次本来就对，只是命中的块里没有内容。**
3. **融合是否占优，取决于被融合那一路的质量。** 在 bm25 还有 bug 的时候，RRF（79.4%）明显输给纯向量（83.4%），看起来像"等权融合引入了字面噪声"；修好 bm25 后 RRF 反超向量（89.9% > 88.9%），holdout 上差距更大（93.5% > 90.3%）。**同一句"融合不占优"的结论，换一个 bug 就反转了**——所以看到融合没涨，先怀疑单路实现，再怀疑融合策略。
4. **排序该交给能读内容的模型。** 宽召回（每路 20 条）→ RRF 合并（取 10 条）→ rerank 精排（取 3 条）把 Top-1 从 89.9% 提到 96.0%，是各环节里收益最大的一步（相对最强单路 +7.1 个点）。
5. **rerank 补 Top-1，也小幅补召回。** hybrid 的 recall@3 为 0.985，略高于纯向量（0.980）。它不理解"这题需要两块拼起来"，但宽召回（每路 20 条）先把候选池撑大，rerank 再在池内精排，跨块题的第二块因此更少被挤出前 3。
6. **口语问法（L4）是单路检索最吃力的一层。** L4 题上字频 61.0%、bm25 63.4%、向量 82.9%，hybrid 95.1%——问法越像真人，流水线相对单路的优势越大。


### 端到端：检索提升未转化为回答质量

| 检索器 | 检索命中率 | 回答通过率 |
|---|---|---|
| freq | 93.1% | 93.1% |
| embed | 96.6% | 93.1% |

embed 检索命中率更高（多召回一道跨块题），但回答通过率相同：跨块题的答案分散在多个块中，Top-K=3 的上下文容量不足以完整承载，模型仍拿不到完整信息。

**改进方向**：增大 Top-K、多路融合或重排（rerank）。

> 已实施：宽召回 + RRF 合并 + rerank 精排（`config.RETRIEVER = "hybrid"`），
> 检索 Top-1 从 89.9%（全量 RRF）提升到 96.0%，见上一节。rerank 不可用时自动降级回 RRF 顺序，
> 向量服务不可用时降级回 BM25，保证链路不因单个组件失效而中断。

### 切块参数对照

检索器固定为字频（Top-3），只变切块方式，比较各切法之间的相对差异：

| 切块方式 | 块数 | Top-3 命中 | 标志词召回率 |
|---|---|---|---|
| heading 按标题 | 54 | 94.5% | 80.1% |
| fixed 300 字 | 26 | 94.0% | 80.6% |
| fixed 500 字 | 15 | 91.0% | 80.6% |
| fixed 800 字 | 9 | 95.5% | 83.0% |

在 54 块、约 7000 字的规模下，四种切法的命中率差异不大（91%～95.5%），fixed/800 反而略高（95.5%）。但仍采用 heading 切块：校园知识天然"一个标题一个知识点"，按标题切语义边界更清晰，引用时能直接定位到标题；fixed 会在标题中间断开，跨块题反而更难拼。

## 工程记录

1. **字频检索的误召回**：查询"什么是 RAG"时 Top-1 召回"ReAct 循环"（字符重叠所致），由 Top-K 兜底。说明 Top-K 是对检索误差的余量设计，代价是引入无关上下文。
2. **注入攻击评测需构造有效样本**：转账/忽略规则类指令对 DeepSeek 无效；使用"伪装教务处修改选课时间"类事实篡改样本才得到稳定差异：未加固版本受骗，加固版本（`<untrusted_data>` 信封隔离）守住。
3. **上下文压缩会丢失关键事实并引发幻觉**：删除"研二专硕找算法实习"后，模型生成错误推断。上下文压缩的目标是保证关键事实不被幻觉覆盖，而非仅节省空间。
4. **tool_call_id 无法跨会话持久化**：将 tool 中间产物持久化到文件后，重启导致引用失效。持久化仅保存干净的问答对。
5. **向量检索开销优化**：缓存、批量请求、索引落盘三层优化，冷启动请求数从 37 次降至 2 次。
6. **全局单例会话会串话**：初版 Web 服务用一个全局 agent，所有访客共用同一份 `messages`，第二个用户能看到第一个用户的上下文。改为按 cookie 分配会话、记忆按会话分文件，并用两个独立客户端做隔离验收。

## 快速开始

### 方式一：Web Demo

```bash
pip install -r requirements.txt
python web_demo.py               # 或运行 run_web.bat
```

浏览器打开 `http://127.0.0.1:8000`。页面展示答案及本轮检索命中的知识块（含相关度），顶部为四项核心评测数字。

### 方式二：命令行

```bash
pip install -r requirements.txt   # 依赖 openai + jieba + dashscope + flask
cp .env.example .env              # 配置 DEEPSEEK_KEY 与 DASHSCOPE_KEY
```

```bash
运行 run.bat        # 对话（/hits 查看检索命中，/history /clear）
运行 run_eval.bat   # 运行评测，结果写入 reports/
```

**调参 / 考试分开跑**（避免在评测集上调参）：

```bash
python src/eval_retrieval.py --split dev      # 只跑调参集（149 题）
python src/eval_retrieval.py --split holdout  # 只跑独立评测集（65 题，报成绩用）
python src/eval_pipeline.py --split dev       # 五方案对照·调参集
python src/eval_pipeline.py --split holdout   # 五方案对照·独立评测集
```

最终评测的原始输出保存在 `reports/final/`（调参集 137 题 / 独立集 62 题 / 全量 199 题三份），审读代码与结论无需配置密钥。

## 部署

### Docker

```bash
docker build -t campus-rag-agent .
docker run -p 8000:8000 \
  -e DEEPSEEK_KEY=... \
  -e DASHSCOPE_KEY=... \
  campus-rag-agent
```

生产启动方式为单进程多线程（`gunicorn -w 1 --threads 16`）。

### 服务端行为

| 能力 | 实现 |
|---|---|
| 会话隔离 | 按 cookie 分配会话，历史按会话落盘（`data/memory/<session_id>.json`），访客之间不共享上下文 |
| 并发 | 每会话一把锁，同一用户的并发请求串行处理，避免对话历史被交叉写入 |
| 降级 | rerank 失败回退 RRF 顺序；向量服务失败回退 BM25；模型调用超时重试 2 次，仍失败返回可读提示而非 500 |
| 限流 | 同一 IP 每分钟 12 次，超限返回 429 |
| 健康检查 | `GET /health` 返回知识库块数、会话数、依赖配置状态 |

为什么是单进程：会话状态在进程内存中，多 worker 时同一用户的两次请求可能落到不同进程，表现为刷新后历史丢失。要横向扩容需把会话移到 Redis 等共享存储。

### 验收

```bash
python tests/test_online.py http://127.0.0.1:8000
```

检查健康状态、会话内记忆、访客隔离、限流四项，会真实调用模型（约 10 秒）。

## 技术栈

Python 3.11+ · DeepSeek · 阿里云 text-embedding-v3 · gte-rerank-v2 · jieba · Flask · gunicorn

不依赖 Agent 框架：ReAct 循环、检索器、上下文拼装、评测均为自行实现。
