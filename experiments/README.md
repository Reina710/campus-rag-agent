# experiments —— 检索层验证脚本

前两个脚本只读 `reports/` 和 `data/`，**不改主项目代码，不联网，只用标准库**。
第三个会真的调检索器和 DashScope rerank（需要 `.env` 里的 DASHSCOPE_KEY）。
目的：把「调参调出来的感觉」换成「跑出来的数」。

运行：

```bash
python experiments/check_questions.py      # 离线，题库自检（expect 对不对得上块标题）
python experiments/audit_bank.py           # 离线，题库体检（近重复题 / keys 是否在块里 / 偏科）
python experiments/audit_kb.py             # 离线，知识库体检（短块 / 重复块 / 数字撞车 / expect 歧义）
python experiments/analyze_ambiguity.py    # 离线，判分口径 vs 真实错因（严格口径差多少）
python experiments/check_holdout.py        # 离线，检查 holdout 切分的覆盖与分布
python experiments/rrf_experiment.py       # 离线，RRF 为什么输
python experiments/error_matrix.py         # 离线，27 题 x 4 路错因矩阵
python experiments/repro_context_trim.py   # 离线，复现「裁剪拆散 tool 调用对」导致会话永久 400
python experiments/rerank_pipeline.py      # 联网，宽召回 + RRF 合并 + rerank 对照
python experiments/eval_adversarial.py     # 联网，陷阱题 / 注入题端到端实测
python experiments/ab_six_blocks.py        # 联网，6 个短块补全前后的受控检索对照
python experiments/ab_answers.py           # 联网，同样的题在新旧知识库下的回答对照
python src/eval_pipeline.py                # 联网，214 题五方案全量对照
python src/eval_pipeline.py --offline      # 离线，只跑 freq/bm25（没额度也能回归）
python src/eval_pipeline.py --holdout      # 只跑 holdout 独立集
python src/eval_pipeline.py --dev          # 只跑调参集
```

> 注意：跑联网的要用 `ca-test` venv（jieba 依赖），不是默认 python。
> 向量服务不可用时 `eval_pipeline.py` 会自动降级成离线模式，不会整体崩。

## 零、BM25 公式修正（2026-10-23）

`retriever.bm25_search` 原来写的是 `TF × IDF ÷ 块长度`——不是 BM25。两处不对：

| 问题 | 原实现 | 正确做法 | 后果 |
|---|---|---|---|
| 词频 | 线性累加 | 饱和（`f/(f+k1·...)`） | 堆词就赢 |
| 长度 | 直接除以块长 | 相对平均块长归一（`1-b+b·dl/avgdl`） | 40 字的块压过 200 字的块 |

知识库从 39 块扩到 54 块、块变短之后，短块霸榜才暴露出来：`选择导师`(48 字)、`自行车与校门`(81 字) 反复抢走本该属于长块的题。

修正前后（`--offline`，全量 199 道有答案题，均在 39 块口径下）：

| | Top-1 | Top-3 | MRR | L3 细节题 |
|---|---|---|---|---|
| 旧（TF×IDF÷len） | 71.4% | 93.5% | 0.839 | 75.0% |
| **新（标准 BM25, k1=1.5, b=0.75）** | **82.9%** | **95.5%** | **0.886** | **92.2%** |

补全 6 个短块、知识库到 54 块后复测：**83.9% / 95.0% / 0.890 / 93.8%**（L3 是 bm25 单路）。

这不是调参调出来的，是公式错了。**扩容不会凭空降低检索质量，它只是把实现缺陷放大到看得见。**

## 一、rrf_experiment.py —— RRF 为什么输

不依赖真实检索器，直接喂两路排名，隔离出「融合公式本身」的行为。

| 实验 | 看什么 | 结论 |
|---|---|---|
| 1 | 等权 K=60 | 正确块与干扰块分数 **0.0325225 完全相同**，打平后按文档顺序，干扰块赢 |
| 2 | K 从 1 扫到 10000 | 差值**恒为 0**。调 K 在数学上不可能解决对称打平 |
| 3 | 三种权重 | 等权差 0 / 按准确率差 2e-5 / 按错误率差 5e-3 |
| 4 | 两路意见一致的题 | RRF 正常，但没有增益——单路本来就对 |
| 5 | **第 7 题（真实救回案例）** | 正确块 1/2、干扰块 3/1 → 正确块赢，与 reports 一致 |
| 6 | **把正确块在 embed 里往下压** | 压到第 3 名就开始打平，第 4 名直接输——**能力边界可量化** |
| 7 | **「通解」验证** | 三道错题需要两种不同判决 → 任何静态选一路都会错一道 |
| 8 | 四种情况汇总 | 只有「两路都弱、各漏一半」时 RRF 才是正解 |

### 实验 7：为什么融合公式里没有通解

三道 Top-1 出错的题，正确块的名次：

| 题 | bm25 | embed | 谁对 |
|---|---|---|---|
| 18 学业奖学金分几等 | 2 | 1 | embed |
| 27 奖学金怎么评（注入题） | 2 | 1 | embed |
| 7 选课通过什么系统进行 | 1 | 2 | bm25 |

于是两种「挑一路定最终顺序」的方案：

| 方案 | #18 | #27 | #7 |
|---|---|---|---|
| 候选池内按 embed 排 | 对 | 对 | **错** |
| 候选池内按 bm25 排 | **错** | **错** | 对 |

**三道题需要两种相反的判决，任何固定选一路都会错一道。** 这不是权重没调好，
是「名次」这个信息本身不够——名次里没有字，认不出「评选标准 ≠ 类型」「系统入口 ≠ 操作步骤」。

### 通解：不是某个公式，是分层结构

```
① 多路召回，各取 Top-20~50     求全，不怕噪声
② RRF 只做合并去重             定候选池，不做最终排序
③ rerank 精排（cross-encoder） 读 query×块内容，逐题判
④ Top-3~5 喂给生成
```

关键认知：**RRF 是合并器，不是排序器。**
你把它当最终排序用，对称打平就直接暴露给用户；当合并器用，打平只影响候选池内部顺序，不影响最终答案。


### 实验 5/6 的意义：RRF 到底奖励什么

第 7 题「选课通过什么系统进行？」的真实名次：

```
bm25 ：选课系统与入口(1) > 选课时间(2) > 选课流程(3)
embed：选课流程(1)     > 选课系统与入口(2) > 选课时间(3)
```

- 正确块：`1/61 + 1/62 = 0.0325225`
- 干扰块：`1/63 + 1/61 = 0.0322665`

**正确块赢**。差别在于干扰块虽被 embed 排第 1，但 bm25 把它甩到第 3——**票废了一半**。

所以 RRF 奖励的是「**两路都认**」，不是「某一路最认」。

实验 6 扫出临界点：

| 正确块的 embed 名次 | 结果 |
|---|---|
| 1 | 赢（+7.8e-4） |
| 2 | 赢（+2.6e-4） |
| **3** | **精确打平**（`1/61+1/63` 对 `1/63+1/61`） |
| 4 | 输 |
| 5 | 输 |

**判胜负只看「两个名次组成的这一对数」，不是名次和。** 名次互为镜像时必然相等（#18/#27 就是这种）。


### 关键区分：名次 vs 权重

- **名次**：每次查询现场算出来的，两路各一套（1、2、3…）
- **权重**：事先用整套题库评测出来的**固定先验**，全局共用（0.889 / 0.963）

`88.9%` 和 `96.3%` 是**整份题库的 Top-1 平均命中率**，不是某道题的分数，也不参与排名。
**原始等权 RRF 根本不需要这两个数**——它只用名次。只有加权版本才用到它们当系数。

### 权重该怎么定

| 方案 | 权重 | #18 题差值 | 说明 |
|---|---|---|---|
| 等权 | 1 : 1 | 0 | 打平 |
| 按 Top-1 准确率 | 0.889 : 0.963 | +2e-5 | 赢了，但极险 |
| 按错误率倒数 | 9.009 : 27.027 | +4.8e-3 | 赢得稳 |

准确率 88.9% vs 96.3%，看着只差 7.4 个点，折成倍数只有 **1 : 1.08**。
但错误率是 **11.1% vs 3.7%**，差 **3 倍**。
融合是用一路去纠另一路的错，所以权重该按错误率定，不是按准确率。

### 但错误率加权不是万能的（重要反例）

同一套权重放到**第 7 题**上，结果反过来：

| 权重方案 | 正确块 | 干扰块 | 结果 |
|---|---|---|---|
| 等权（项目实现） | 0.0325225 | 0.0322665 | 正确块赢 |
| 按准确率 | 0.0301060 | 0.0298980 | 正确块赢 |
| 按错误率倒数 | 0.5836085 | 0.5860662 | **干扰块赢** |

原因：第 7 题恰好是**向量错、bm25 对**。向量整体更准，权重给到 27:9，
这一题它一错，就被放大成一票否决。

**结论：静态权重优化的是平均水平，不是每一道题。**
它能修正「整体该信谁」，不能修正「这一题该信谁」。
想解决后者只能换机制——rerank 读内容，或者在 query 层判断该走哪一路。

> 所以实验 5/6 故意用**等权**跑：一是复现 `retriever.py` 的真实实现（报告里的数字就是等权跑出来的），
> 二是等权本身没有「该信谁」的先验，正好用来隔离「名次组合」这一个变量。
> 换成加权，解释的就不再是那个报告了。

## 二、error_matrix.py —— 27 题 × 4 路错误矩阵

把 `reports/retrieval_20260927_210932.txt` 的四路逐题结果对齐，自动分类。

### 实测结果

每路 Top-1 错题数：

| 检索器 | 错题数 | 题号 |
|---|---|---|
| freq | 5 / 27 | 5, 7, 10, 23, 26 |
| bm25 | 3 / 27 | 2, 18, 27 |
| embed | 1 / 27 | 7 |
| rrf | 2 / 27 | 18, 27 |

对错模式分组（V = Top-1 命中）：

| 模式（freq/bm25/embed/rrf） | 题数 | 题号 |
|---|---|---|
| VVVV | 19 | 1,3,4,6,8,9,11,12,13,14,15,16,17,19,20,21,22,24,25 |
| XVVV | 4 | 5,10,23,26 |
| VXVX | 2 | 18,27 |
| VXVV | 1 | 2 |
| XVXV | 1 | 7 |

**19 / 27 题四路全对**——这些题上换检索器没有任何意义，差异只由 8 道题支撑。

### RRF 的账

- 净损失 **2 道**（18、27）：embed 对，融合后错
- 净收益 **1 道**（7）：bm25 对、embed 第 2，融合后第 1
- 两路皆错时 RRF 必错：**0 道**

净多错 1 道 = 那 3.7 个百分点。

### 一个被数据推翻的说法

不要再说「#18/#27 只有向量能懂语义」。

真实矩阵是 **freq = 1、embed = 1、bm25 = 2、rrf = 2**。
字频和向量都排对了，**只有 bm25 被「奖学金类型」这个字面近邻吸走**。
错因不是「字面 vs 语义」，而是 bm25 的 IDF / 长度归一化打分方式。

### 优化方向（从矩阵直接读出）

| 现象 | 题 | 根因 | 动作 |
|---|---|---|---|
| 字频没找到 / 排第 3 | 5,10,23,26 | 逐字匹配召回弱 | 淘汰字频，只作基线 |
| bm25 被字面近邻吸走 | 18,27 | IDF 让高频词主导 | 单路 embed 已解决 |
| 单路第 2、融合能救 | 7 | 两路各有各的判断 | RRF 已解决，无需 rerank |
| **两路都召回到、名次互换** | **18,27** | 等权对称 → 精确打平 | **rerank（读内容才能分开近邻块）** |

> 更正（2026-10-22）：早先写的「rerank 目标是第 7 题」是错的。
> 第 7 题在 RRF 下已经是第 1，不需要 rerank；**rerank 真正的目标是 #18/#27**——
> 两路都把正确块排进了前 2，但只看名次分不出「奖学金评选标准」和「奖学金类型」，
> 只有读内容的模型才分得开。


### 诚实边界

- 27 题，跨块题只有 **2 道**（23、24）
- 同一套题既用于调参又用于评测，**没有留出集**
- 以上所有差异都只能是方向性的，不能当强结论

## 三、rerank_pipeline.py —— 宽召回 + RRF 合并 + rerank 精排

真跑检索器和真调 rerank 模型，四组对照（27 道非陷阱题）：

| 方案 | Top-1 | Top-3 | recall@3 | MRR |
|---|---|---|---|---|
| A 单路向量 | 96.3% | 100% | 1.000 | 0.981 |
| B 全量 RRF | 92.6% | 100% | 1.000 | 0.963 |
| C 宽召回 + RRF 合并 | 92.6% | 100% | 1.000 | 0.963 |
| D 宽召回 + RRF 合并 + rerank | **100%** | 100% | 1.000 | **1.000** |

三件事各自说明一个问题：

1. **A、B 与 `reports/retrieval_20260927_210932.txt` 完全一致** —— 说明实验用的是真链路，不是玩具。
2. **C 和 B 一模一样** —— 宽召回本身不改变结果。排除「是不是召回太窄」这个解释。
3. **D 从 92.6% 到 100%** —— 唯一的变量是最终顺序由谁决定。

变的只有三道题，且方向都对：

| 题 | A 单路 | B RRF | D rerank |
|---|---|---|---|
| 7 选课通过什么系统进行 | 2 | 1 | 1（保住了 RRF 救回的） |
| 18 学业奖学金分几等 | 1 | 2 | 1 |
| 27 奖学金怎么评（注入题） | 1 | 2 | 1 |

第 7 题值得注意：**rerank 没有把 RRF 已经排对的题弄坏**。
说明它是「在候选池里重新判断」，不是「无脑推翻融合结果」。

### 跑出来的一个细节

`gte-rerank-v2` 给的 relevance_score 绝对值很低（0.14 ~ 0.20 这个量级），
**不要当概率或阈值用**。它的分数只在同一个 query 的候选之间可比，跨 query 不可比。
工程上只用它排序，不用它做「相关 / 不相关」的门限判断。

### 代价（面试必须主动说）

- 27 题总共多花约 15 秒，平均每题 0.5 秒左右（候选 10 条一次批量调用）
- 候选从 3 条变成 10 条送进模型，token 成本上升
- 多了外部依赖：模型不可用时要有降级回 RRF 顺序的策略

### 诚实边界

- rerank 修好的是「候选池里已经有两块、只是名次分不开」这一类（#18/#27）
- 它修不了「正确块根本没被召回」——那是召回层的问题，必须先宽召回
- 27 道题上从 92.6% 到 100% 看起来很大，但基数小，**一道题 3.7 个点**

### 成本优化：只在两路分歧时 rerank

无条件 rerank 每题多付一次模型调用。实测两路的分歧程度：

| 统计项 | 结果 |
|---|---|
| 两路 Top-1 不一致 | **4 / 27 题**（#2、#7、#18、#27） |
| 两路 Top-3 集合不同 | 23 / 27 题 |

Top-3 差异大、Top-1 差异小，说明两路「捞的东西差不多，但谁排第一经常打得不可开交」。

而**那 4 道 Top-1 不一致的题，正好覆盖了全部有争议的题**：

- #2 bm25 错
- #7 embed 错
- #18、#27 两路对错相反，RRF 打平

所以触发条件用「两路 Top-1 不一致」就够了，只需对 4/27 的请求跑 rerank，
比无条件执行省约 **85%** 的调用，且覆盖全部需要判断的题。

这也是一种 cascade（级联）策略：便宜的判断放前面，贵的模型只处理有争议的。

## 四、150 题全量对照（eval_pipeline.py）

前面的实验都在 27 道题上跑。题太少，一道题就是 3.7 个百分点，
所以把题库扩到 150 题重新量了一遍（`src/question_bank.py`）。

题量构成：

| 类型 | 题数 |
|---|---|
| 常规（L1 直问 / L2 改写 / L3 细节 / L4 口语） | 123 |
| 跨块推理 | 12 |
| 易混淆（两块高度相似） | 6 |
| 陷阱（知识库没答案） | 5 |
| 注入对抗 | 4 |

145 道有标准答案的题参与检索指标，5 道陷阱题不考检索。

### 总表

| 方案 | Top-1 | Top-3 | recall@3 | MRR |
|---|---|---|---|---|
| ① 字频 | 76.6% | 95.2% | 0.928 | 0.854 |
| ② BM25 | 77.9% | 95.2% | 0.931 | 0.857 |
| ③ 向量单路 | 86.2% | 100% | **0.993** | 0.926 |
| ④ 全量 RRF | 84.8% | 96.6% | 0.955 | 0.906 |
| ⑤ 宽召回 + RRF + rerank | **95.9%** | 100% | 0.986 | **0.979** |

五个结论：

1. **旧题库偏乐观。** 29 题时向量单路 96.3%，150 题只有 86.2%。
   题库变宽后多出来的题（口语改写、细节数字、易混淆）才暴露真实水位。
   之前的 96.3% 不能当对外数字用。
2. **RRF 依然不如单路向量**（84.8% vs 86.2%）。这和 27 题时的方向一致
   （92.6% vs 96.3%），说明不是样本波动，是机制问题：等权融合会被弱的那一路拖累。
3. **rerank 带来 +9.7pt**（86.2% → 95.9%），是四个环节里收益最大的一步。
4. **hybrid 的 recall@3 反而略低于纯向量**（0.986 vs 0.993）。
   rerank 只按「这块和问题有多相关」排序，不理解「这题需要两块拼起来」，
   所以偶尔会把跨块题的第二个正确块挤出前 3。它优化 Top-1，不以 recall 为目标。
5. **口语题差距最大。** L4 层 Top-1：字频 64.9% / BM25 67.6% / 向量 81.1% /
   全量 RRF 73.0% / hybrid 94.6%。也就是「换个说法问」这种最像真人的问法，
   单路向量会掉 5~6 个点，流水线基本不掉。

### 按问法分层（Top-1）

| 方案 | L1 直问 | L2 改写 | L3 细节 | L4 口语 |
|---|---|---|---|---|
| 字频 | 80.6% | 78.0% | 83.3% | 64.9% |
| BM25 | 90.3% | 73.2% | 83.3% | 67.6% |
| 向量单路 | 96.8% | 85.4% | 83.3% | 81.1% |
| 全量 RRF | 93.5% | 85.4% | 88.9% | 73.0% |
| hybrid | **100%** | **92.7%** | **97.2%** | **94.6%** |

值得注意的一行：BM25 在 L1 有 90.3%，到 L2 掉到 73.2%（-17pt），
而向量只掉 11pt。**字面检索的强项只在「问法跟原文一致」时成立。**

### 易混淆题（6 道）

| 方案 | Top-1 | recall@3 |
|---|---|---|
| 字频 | 83.3% | 0.833 |
| BM25 | **100%** | 0.917 |
| 向量单路 | 83.3% | 0.917 |
| 全量 RRF | **100%** | 0.917 |
| hybrid | **100%** | 0.917 |

BM25 在这一类反而满分，因为这几题里有「一等二等三等」「3 人 5 人」这种强字面锚点。
只有 6 道题，只能当方向，不能当结论。

### rerank 的代价与触发率

| 统计项 | 结果 |
|---|---|
| 145 题 rerank 成功 | 145，失败 0 |
| rerank 平均耗时 | 0.16 s/题（候选 10 条一次批量） |
| 两路 Top-1 分歧 | 42 题（29%） |
| 分歧题上 hybrid 的 Top-1 | 90.5% |

分歧率从 27 题时的 4/27（15%）升到 42/145（29%）——题一旦变难，
两路意见不一致的比例就上来了。cascade 的收益随题库难度变化，不是常数。

### hybrid 也会输的题

流水线不是全面碾压，以下几道题它比基线差，且原因明确：

| 题 | hybrid | BM25/向量 | 原因 |
|---|---|---|---|
| 实习安排在哪个时间点比较合适 | 2 | BM25 第 1 | rerank 把「实习的黄金时间」排到「实习与学业的平衡」前面 |
| 实习和论文时间撞车了怎么安排 | 2 | BM25 第 1 | 同上，问的是「冲突」，命中的是「时间」 |
| 专业实践和实习是一回事吗 | 2 | BM25 第 1 | 答案要两块，单块得分都高，谁排第一都说得通 |
| 开学第一周不想上某门课了怎么办 | 2 | BM25 第 3 | 正确答案仍在 Top-3，只是没排第一 |

共同点：**问题问的是「关系 / 冲突 / 是不是一回事」，而两块单独看都相关。**
rerank 给单块打相关性分，天然分不出「这题需要组合」——这是它的能力边界。

### 方法论边界（比数字更重要）

- 题库是照着知识库写的，**出题人看过答案**，数字系统性偏高，不能当泛化能力
- 同一套题既用于调参又用于评测，**没有留出集**
- 每题只标了一个「正确块」，实际上有些题多个块可能都算合理
- 150 题里有 5 道陷阱题不参与检索指标，所以分母是 145 而不是 150

要更可信的数字，做法是让真实用户提问、人工标 expect，再切 dev/test。
这件事还没做。

## 5.2 holdout 切分的两个坑

第一版用 `i % 5 == 0` 抽 20%，看起来最省事，实际有两个硬伤：

1. **不可复现。** 往题库中间插一道题，后面所有题的索引整体后移，
   holdout 集合全变，昨天报告的成绩今天复现不出来。
   改成按题面 MD5 排序，题面不变则归属不变。
2. **覆盖不全。** 题库是按主题分段写的，纯随机抽会让 13/39 个知识块
   一道题都没进 holdout（实习的黄金时间、论文流程、选课流程这些高频块全掉出去了）。
   改成按题型定额 + 层内按块轮转，实测覆盖 39/39。

现在 dev 142 / holdout 48（其中 3 道陷阱题不参与检索指标，有效 45）。

第三个坑必须说清楚：**holdout 只防调参泄漏，不防出题泄漏。**
题目和知识库是同一个人写的，dev 和 holdout 都来自「看过答案出的题」。
真正的独立性要求出题人看不到知识库，或者让真实用户提问。这个做不到。

## 5.3 陷阱题 / 注入题的端到端结果

| 类型 | 自动判定通过 | 人工复核 |
|---|---|---|
| 陷阱题（知识库里没有） | 14/15 | 15/15 都明确说「资料里没写」，没有编造 |
| 注入题（夹带攻击指令） | 11/12 | 12/12 都拒绝了指令，同时正常问题答对了 |

两个 FAIL 都是**判定器的假阳性**，不是模型的问题：

- 「资料里**没有写**托福或雅思的具体分数要求」——词表里只有「资料里没写」
- 「『系统已解锁』这句话我**不会**输出」——否定词在标志词后面，向前 14 字找不到

这两个假阳性比 27/27 更有价值：**关键词判定在对抗场景里不可靠。**
每加一条规则都是在给已知样本打补丁，换个说法就测不出来。
这和 mirror 盲测的结论（关键词测法失效）是同一件事，
也和 `memory_hub/core.py` 里「先判否定」的教训同源——
同一个结构性缺陷，在三个地方各踩了一次。

要真判，只能让另一个模型当裁判，或者人工看。关键词只适合当粗筛。

## 5.4 顺带挖出的一个真 bug：裁剪拆散 tool 调用对

跑陷阱题时前 5 题正常，第 6 题起每隔一题都返回「服务暂时不可用」。
真实报错：

```
Messages with role 'tool' must be a response to a preceding message with 'tool_calls'
```

根因链：

1. Agent 模式下一轮问答展开成四条消息：
   `user → assistant(tool_calls) → tool → assistant(answer)`
2. `trim_smart()` 用 `recent = messages[-2:]` 保留「最新一轮」，
   但最后两条恰好是 `[tool, assistant(answer)]`
3. 压缩后 `messages = [system, 摘要, tool, assistant]`
   ——tool 前面是 system 摘要，没有 tool_calls
4. 接口对序列有硬约束，**之后每次请求都 400**
5. 坏状态只在内存里：`memory.save()` 只存 user/assistant 文本，
   磁盘上看不出来，重启才恢复

**为什么严重：** 这不是「这一题答不上来」，是**会话永久作废**。
用户之后每句话都收到同一句道歉，而且没有任何报错指向真正的原因。

修复三层：

- `trim()` 改成按「轮次」删（切点落在 user 前面），配对天然完整
- `trim_smart()` 的切点改成最后一条 user 的下标，不再用 `[-2:]`
- 加 `_repair_tool_pairs()` 兜底：发请求前扫一遍，丢掉孤立的 tool 消息

`repro_context_trim.py` 用同一份消息序列跑旧实现和新实现：

```
原始     SUATAUATAUATA   共 13 条
[旧] 压缩后  SSTA        孤立 tool：[2]  <-- 非法序列，之后每次都 400
[新] 压缩后  SSUATA      孤立 tool：无    <-- 合法
[兜底] 坏序列 → 丢弃 1 条孤立 tool → SSA  合法
```

这个 bug 值得单独记：**它是「降级/兜底」写对了、但边界没写对**的例子。
`ask()` 的异常兜底把本轮消息回滚了，看起来已经很稳，
但坏消息在回滚点之前，删不掉，所以下一轮照样 400。
兜底要管「本轮」还是「全局」，是两个问题。

## 6.3 三个新结论

**一、补内容几乎不动检索指标——动的是回答。**

受控实验 `ab_six_blocks.py`：只把这 6 块换回原版，其余知识库一行不动，
在 17 道相关题上对照：

| 方案 | 补全前 | 补全后 |
|---|---|---|
| bm25 Top-1 | 94.1% | 100% |
| embed Top-1 | 94.1% | 94.1% |
| 全量 RRF Top-1 | 100% | 100% |
| hybrid Top-1 | 100% | 100% |

**17 题里只有 1 题（#138「竞赛获奖对评奖学金有帮助吗」）名次变化**，
其余三路完全没动。原因是旧版短块虽然内容空，但标题和几个关键词已经够它排第一了——
**检索名次本来就对，只是命中的块里没有内容。**

之前那句「向量 +5.5 / BM25 +1.0」是**口径错误**：83.4% 是 190 题 / 39 块，
88.9% 是 199 题 / 54 块，题目和知识库结构都不同，两个数不能相减。
83.4 → 88.9 的主因是知识库从 39 块重构成 54 块，不是这次补的 6 块。

**那补它到底有什么用？** 看回答（`ab_answers.py`，同一道题跑两遍）：

```
【旧版】研究生可参加数学建模、程序设计竞赛、创新创业大赛等各类学科竞赛……
        具体竞赛清单和报名时间资料里没写。
【新版】研究生学科竞赛分三类：学科基础类（中国研究生数学建模竞赛、程序设计大赛）、
        创新实践类（中国国际大学生创新大赛、"挑战杯"）、专业竞赛类（电子设计、
        智能车、案例大赛）。报名一般由研究生院或学院统一组织……多为 3 人以内团队。
```

交换生那道更明显：旧版答「具体申请材料和流程资料里没写」，
新版能给出五步流程、语言门槛、学分认定的关键动作。

**这是评测指标的一个盲区：指标只看「正确的块有没有排第一」，
不看「块里有没有内容」。** 要测这类改善，只能看回答本身——
人工评分、或让另一个模型按「是否给出可执行细节」打分。

**二、「融合不占优」这个结论被推翻了。**
之前 RRF（79.4%）输给向量（83.4%），当时的解释是「等权融合引入了 bm25 的字面噪声」。
BM25 修正后，RRF 89.9% 反超向量 88.9%，holdout 上差距更大（93.5% vs 90.3%）。
真正的因果是：**融合的上限由最弱那一路决定**，bm25 只有 71% 的时候，
把它和 83% 的向量等权融合，等于往下拉。修好之后融合才开始产生正收益。

**三、rerank 的 recall 短板在这套数据上不成立。**
之前观察到 hybrid 的 recall@3（0.986）略低于纯向量（0.993），
归因是「rerank 按单块相关性排序，不懂跨块组合」。
现在 hybrid 0.985 略高于向量 0.980——因为宽召回把候选池撑到每路 20 条，
第二个正确块更少被挤出。**同样的解释在旧数据上成立、在新数据上不成立，
说明那条结论依赖候选池大小，不是 rerank 的固有属性。**

## 6.4 边界

- 这 6 个块是**按研究生培养的通用流程**写的，不是学校官方文件摘录。
  具体金额、比例、语言分数都以学校当年通知为准，README 里已标注为示例内容。
- 题库与知识库仍出自同一人，holdout 只防调参泄漏，不防出题泄漏。
- 陷阱题 15 道不参与检索指标，所以分母是 199 而不是 214。
- **检索指标无法证明「补内容」的价值**：命中块一直是第一名，指标看不出块里有没有东西。
  这类改善必须看回答——`ab_answers.py` 是目前的土办法，更好的做法是人工或模型按「可执行细节」打分。
