# 反馈（点赞 / 点踩）

## 一句话

**每条回答下面有 👍 有用 / 👎 没用，用户点一下，就记一条到 `data/feedback.jsonl`。**

## 为什么需要

没有反馈，你就不知道"哪些题答得不好"。评测集是**你猜的**问题，反馈是**真实用户**遇到的问题——后者才能告诉你下一轮该修什么。

点 👎 的题，就是你的 **bad case 池**：把它们整理进题库，或者拿去看检索为什么没命中。

## 怎么用

1. 打开页面问一个问题
2. 回答下面出现两个按钮：👍 有用 / 👎 没用
3. 点一下，按钮高亮成"已记录"
4. 数据落到 `data/feedback.jsonl`，一行一条

## 数据长什么样

```json
{"ts": "2026-10-24T17:20:00", "rating": "down", "question": "图书馆能借几本", "answer": "...", "request_id": "a1b2c3", "session": "xxx"}
```

| 字段 | 含义 |
|---|---|
| `rating` | `up` / `down` |
| `question` | 用户问的原话 |
| `answer` | 当时给出的回答 |
| `request_id` | 和服务端日志里的 `rid` 对得上，能串起完整请求 |
| `session` | 哪个浏览器 |

## 接口

```bash
# 提交反馈
curl -X POST localhost:8000/api/feedback \
  -H 'Content-Type: application/json' \
  -d '{"rating":"down","question":"...","answer":"..."}'

# 看汇总
curl localhost:8000/api/feedback/stats
# {"total": 10, "up": 7, "down": 3, "up_rate": 0.7}
```

## 代码在哪

| 文件 | 作用 |
|---|---|
| `web_demo.py` | `POST /api/feedback` 记录、`GET /api/feedback/stats` 汇总 |
| `frontend/src/App.jsx` | 回答下方的 👍/👎 按钮、`sendFeedback` |
| `experiments/harvest_feedback.py` | 把点踩聚合成 bad case 池 |

## 从反馈到评测集（bad case 池）

点踩只是"发现问题"，不是"评测"。中间还需要一步：把点踩的题整理进题库。

```bash
python experiments/harvest_feedback.py                  # 生成 data/bad_cases.md
python experiments/harvest_feedback.py --min-count 2    # 只看被踩 >=2 次的题
```

输出 `data/bad_cases.md`：

- 按题聚合（"图书馆能借几本书"和"图书馆能借几本书？"会合并成一条）
- 按点踩次数排序
- 标注"已在题库"还是"建议补"
- 对不在题库的题，生成可直接粘贴进 `question_bank.py` 的骨架（`expect` 需人工填）

**为什么不能全自动**：点踩 ≠ 答错。用户可能手滑、可能只是不喜欢语气、也可能问题本身模糊。所以脚本只负责"把候选聚起来"，判断"是不是真错了"仍然要人看一眼——全自动会把噪声塞进评测集，反而污染指标。

完整链路：**用户点踩 → bad case 池 → 人工确认 → 进题库 → 下次评测自动覆盖**。

## 怎么验证

```bash
# 起服务后，浏览器点一下，然后看文件
tail -n 5 data/feedback.jsonl

# 聚合成 bad case 池
python experiments/harvest_feedback.py
# 看 data/bad_cases.md
```

## 面试怎么说

> "回答下面有点赞点踩，点踩的样本会落到 jsonl 里，带问题和当时答案。这些是真实用户遇到的 bad case，比我自己拍脑袋出的评测题更贴近线上。我会定期把点踩的题捞出来，看是检索没命中还是生成答偏了。"

## 注意

- `data/feedback.jsonl` 是运行时数据，**不要提交到仓库**（建议加进 `.gitignore`）；
- 反馈只记"用户主观判断"，不保证正确，用来**发现问题**而不是**当评测指标**。
